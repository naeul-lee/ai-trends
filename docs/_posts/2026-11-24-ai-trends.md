## 📌 오늘의 한 줄 요약
에이전트를 운영할 때 중요한 건 모델보다 **주변 설계**입니다. OS 수준 샌드박스, 반박하는 검토자 에이전트, 모델에 맞는 "화면 보는 방식"이 성패를 가릅니다.

## 🎯 활용 Best Practice

### 코딩 에이전트 샌드박스: 컨테이너 대신 "호스트를 잠그기" (OpenAI, 11/18)
- Codex는 사용자의 PC를 그대로 쓰되, 명령마다 OS 샌드박스를 씌웁니다. macOS는 Seatbelt, Linux는 bubblewrap과 seccomp를 씁니다. 네트워크는 도메인 허용 목록 프록시를 거치게 하고, 허용된 요청만 DNS를 조회합니다.
- 기본 프로필에서는 작업 폴더만 쓸 수 있고, `.git`·`.codex`는 읽기 전용이며, 네트워크는 꺼져 있습니다. 권한 상승은 명령 단위로 요청하게 했습니다.
- OpenAI가 직접 밝힌 한계도 있습니다. ① 읽기가 넓으면 디스크의 다른 비밀 정보가 노출될 수 있습니다. ② 무시되는 `node_modules`를 조작해 두면 나중에 에디터가 샌드박스 밖에서 실행할 수 있습니다. ③ 와일드카드 도메인과 DNS로 데이터가 새어 나갈 수 있습니다. ④ 금지 glob은 실행 전에 펼쳐지므로 나중에 만들어진 파일은 막지 못합니다.
- **적용 팁:** 사내 에이전트 정책은 "쓰기는 작업 폴더만, `.git`은 읽기 전용, 네트워크는 기본 차단 + 정확한 호스트만 허용"에서 시작하세요. 와일드카드 도메인은 쓰지 마세요. 홈 디렉터리의 `~/.aws`, `.env` 같은 비밀 파일은 읽기도 막으세요.
- 🔗 [OpenAI: Inside the Codex sandbox](https://openai.com/index/inside-the-codex-sandbox/)

### 성능 회귀 조사를 에이전트에게: Performance Factory (OpenAI, 11/19)
- 성능 알림이 울리면 작업이 생깁니다. Codex 에이전트가 원인을 조사해 수정안을 내고, 엔지니어가 검토합니다. 배포 후 수치가 기준선으로 돌아왔는지도 에이전트가 확인합니다.
- 3개월여 동안 조사 1,700건 이상, 원인 규명 600건 이상, 하루 약 17건을 처리했습니다. 원인 제안 100건을 사람이 채점하니 70%가 정확했습니다.
- 핵심 기법은 네 가지입니다.
  - 조사 절차를 `perf-forensics` 스킬로 문서화했습니다.
  - **별도 세션이 진단을 반박**하게 했습니다(적대적 검토).
  - 과거 사건으로 백테스트했습니다. 이때 정답 신호를 지운 상태에서 새 에이전트가 조사하게 했습니다.
  - 매일 에이전트 로그를 점검해 반복되는 도구·권한 실패를 고쳤습니다.
- **적용 팁:** 알림 대응 에이전트는 먼저 "제안까지만" 맡기세요. 평가는 "진단 정확도"와 "요약이 쓸모 있는가"를 따로 재세요. 한쪽이 좋아질 때 다른 쪽이 나빠질 수 있습니다.
- 🔗 [OpenAI Engineering](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)

### 컴퓨터 사용 에이전트: 모델 수준에 맞춰 "보는 방식"을 고르라 (Greptile, 11/19)
- OSWorld 172개 과제로 실험했습니다. 화면 캡처만 주면 약한 모델은 거의 실패했습니다. 접근성 트리를 더하면 GPT-5.2가 15.8%에서 36.2%로, 요소 ID로 클릭하게 하면 52.8%까지 올랐습니다.
- 최상위 모델(GPT-6.1 Sol)은 좌표 클릭 82.7%, ID 클릭 82.1%로 차이가 없었습니다.
- 접근성 트리가 불완전할 수 있다는 점도 확인했습니다. 환경 변수 하나 때문에 GIMP가 트리에서 빠져 있었습니다. 텍스트가 칸을 넘치는 버그처럼 화면으로만 보이는 문제도 있어, 캡처는 함께 줘야 합니다.
- **적용 팁:** 비용 때문에 작은 모델을 쓴다면 "접근성 트리 + 요소 ID 클릭 + 캡처"를 기본으로 하세요. 캔버스나 게임처럼 트리가 없는 화면에서만 좌표 클릭을 쓰세요. 모델을 바꾸면 이 설정을 다시 측정하세요.
- ⚠️ 판매사 자체 실험이고 과제당 1회만 실행했습니다.
- 🔗 [Greptile 블로그](https://www.greptile.com/blog/trex-computer-use)

## ⚙️ LLM 서빙/인프라

### NariQ: Qwen3.8-27B를 10GB로 (Nari Labs, 11/20)
- 코딩 에이전트 실행 기록으로 보정한 3비트 미만 trellis 양자화입니다. BF16 53.8GB가 3비트 10.12GB로 줄었습니다.
- 공개 수치에서 3비트는 BF16과 비슷합니다(DeepSWE 41.0 vs 39.8, Terminal-Bench 63.8 vs 62.6). 2비트는 DeepSWE 28.6으로 확연히 떨어집니다.
- 전용 llama.cpp 포크가 필요하며 Ollama·LM Studio에서는 아직 안 됩니다. AMD·Intel GPU는 지원하지 않습니다.
- **적용 팁:** 로컬 에이전트용 양자화는 3비트까지가 무난해 보입니다. 2비트는 에이전트 작업에서 품질이 크게 떨어지므로, 자신의 과제로 먼저 확인하세요.
- 🔗 [Hugging Face 모델 카드](https://huggingface.co/nari-labs/Qwen3.8-27B-NariQ-GGUF)

## 🏢 업계 동향

### OpenAI·Cisco, 패치 전 공백을 막는 오픈소스 Shirudo (11/23)
- eBPF로 취약한 코드 경로를 재시작 없이 막는 "실드"를 적용합니다. 실드는 에이전트가 만들고, 배포 여부는 보안팀이 결정합니다. 실드에는 서명과 TPM 기록이 붙습니다. BSD-2 라이선스입니다.
- 실험에서는 Codex가 만든 실드가 Elasticsearch를 노린 공격을 막았습니다(통제된 테스트 1건).
- 🔗 [OpenAI 발표](https://openai.com/index/introducing-shirudo/)

### OpenAI 수석 과학자: "perplexity를 업계 공통 지표로" (11/22)
- Jakub Pachocki가 내부 코드 데이터의 log-perplexity를 공유했습니다. GPT-3.5는 약 0.99, GPT-4는 약 0.91이었고, 0.8 아래에서 보안·수학 능력이 급격히 나타났다고 밝혔습니다.
- 이 수치를 기준으로 연구소들이 넘지 않을 "공동 한계"를 정하자고 제안했습니다. 지표의 한계(데이터셋 차이, 추론 효과 미반영)도 함께 적었습니다.
- 🔗 [OpenAI: Perplexity and Intelligence](https://openai.com/index/perplexity-and-intelligence/)
