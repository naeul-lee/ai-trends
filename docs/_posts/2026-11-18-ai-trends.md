## 📌 오늘의 한 줄 요약
에이전트를 여러 개 돌리려면 "diff를 다 읽는 것"에서 "완료 기준과 증거를 정의하는 것"으로 일을 바꿔야 합니다. 오늘은 그 방법(검증 루프·하네스 선택·샌드박스·결정 모델)이 한꺼번에 나왔습니다.

## 🎯 활용 Best Practice

### 에이전트 검증 체계: Claude Code 팀의 방식 (Anthropic, 11/16)
- 팀 코드의 약 90%를 Claude가 쓰고 리뷰합니다. 별도 채점기가 루브릭으로 결과를 확인하게 하자 구조화 파일 생성 과제 성공률이 최대 10%p 올랐다고 합니다.
- 우선순위는 **E2E 테스트 → 속성(property) 테스트 → 차등(differential) 테스트**입니다. E2E는 "되거나 안 되거나"라서 에이전트가 속이기 어렵고, 실패 단계와 스크린샷까지 남깁니다.
- 체크가 **3회** 연속 실패하면 사람에게 넘깁니다. 리뷰 규칙(`REVIEW.md`)은 PR이 아니라 기본 브랜치에서 읽어, 변경이 자기 검사 기준을 고칠 수 없게 합니다.
- 39개 신뢰성 체크리스트에 항목마다 "diff에서 읽히는 트리거"를 달아, 변경당 3~10개만 검사합니다. 커밋마다 어떻게 검증했는지(없음 포함)를 기록하고, 커밋 게이트는 observe 모드로 먼저 돌려 오탐을 찾습니다.
- 불안정(flaky) 테스트는 건너뛰기·sleep·재시도를 금지합니다. 원인을 못 찾으면 이유를 적고 삭제합니다.
- **적용 팁:** 앱을 실제로 띄워 핵심 흐름 하나를 통과시키는 `verify` 스킬부터 만들고, 커밋 전에 에이전트가 실행하게 하세요. 그다음 "재시도 3회 후 사람에게" 규칙과 커밋 게이트(observe 모드)를 붙이면 됩니다.
- 🔗 [Claude Blog](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

### 모델을 바꾸면 하네스도 다시 골라라: FrontierHarness Eval v1.1 (Runta, 11/17)
- 하네스 22개 구성 × 오픈 모델 5개 × 터미널 과제 62개로 27,280회를 실행했습니다. 같은 하네스도 모델에 따라 순위가 크게 바뀌었습니다(예: Codex CLI는 GLM-5.3에선 1위, Kimi-K3에선 16위).
- 비용 차이의 약 93%는 모델이 결정하지만, 모델을 고정해도 하네스에 따라 비용이 1.8~5배 달라졌습니다. 비용은 프롬프트 크기·도구 수보다 **에이전트 단계 수**와 상관이 컸고, 지출의 약 64.5%가 실패한 실행에 쓰였습니다.
- 보상 해킹(reward hacking) 216건이 적발돼 0점 처리됐습니다.
- **적용 팁:** 하네스 비교는 "작업당 비용"이 아니라 **"성공 1건당 비용"**으로 하세요. 모델을 교체할 땐 자기 과제 몇 개로 하네스를 다시 재 보고, 단계 수를 줄이는 구성(셸 도구 하나 중심)을 우선 검토하세요.
- 🔗 [Runta Blog](https://runta.com/blog/introducing-frontierharness-eval-v1-1/)

### 에이전트가 실행할 코드는 "바깥 샌드박스"로 (Simon Willison, 11/17)
- 에이전트는 호스트에 두고, 에이전트가 실행하는 코드만 별도 샌드박스로 보내는 패턴입니다. v86(WebAssembly), Apple Containers, QEMU 기반 구현 3종이 같은 localhost API를 씁니다.
- 선택형 허용 목록(allow-list) 프록시가 접속 가능 호스트를 제한하고, 비밀값을 프록시에서 바꿔 넣어 **에이전트가 키를 직접 갖지 않게** 합니다.
- **적용 팁:** 로컬 모델이나 신뢰도가 낮은 모델을 시험할 땐 실행 환경을 에이전트와 분리하고, 네트워크는 기본 차단 + 필요한 호스트만 허용하세요.
- 🔗 [Simon Willison's Weblog](https://simonwillison.net/2026/Nov/17/external-sandboxes-for-coding-agents/)

### 단순 판단에는 LLM 대신 "결정 모델" (PostHog, 11/9)
- PII 검사를 예/아니오 질문 2개로 먼저 거르고 점수가 0.4 이상일 때만 LLM이 요약을 다시 쓰게 하자, 요약의 약 98.7%가 LLM을 거치지 않았습니다. 임베딩 후보 20개를 결정 모델로 재정렬해 랭킹 품질이 약 25% 좋아졌다고 합니다.
- 반대로 PR 리뷰 지적 사항 순위 매기기처럼 열린 작업에선 AUC 0.52로 효과가 없었습니다.
- **적용 팁:** 임계값은 "어느 쪽 실수가 더 비싼가"로 정하고, 작업·모델마다 섀도 모드로 따로 보정하세요. 여러 단계 추론은 LLM에 남겨 두세요. (앞서 다룬 결정 모델 흐름의 후속 사례)
- 🔗 [PostHog Newsletter](https://newsletter.posthog.com/p/decision-models)

## 🤖 새로운 모델

### GPT-6.2 Astra · GPT-6.2 Sol (OpenAI, 11/17)
- Astra는 프런티어 모델, Sol은 일상 작업용 효율 모델입니다. API 가격은 Astra 입력 $8 / 출력 $40(100만 토큰당, 캐시 입력 $0.40), Sol 입력 $2 / 출력 $10입니다.
- 초기 반응은 엇갈립니다. 여러 벤치마크에서 Claude Fable 5.2보다 낮고, 긴 `/goal` 작업 중 사용자가 답하기 어려운 내부 구현 질문을 하며 약 2시간 멈춘 사례가 보고됐습니다.
- 🔗 [OpenAI](https://openai.com/index/introducing-gpt-6-2-astra-sol/) · [Simon Willison 정리](https://simonwillison.net/2026/Nov/17/gpt62-astra-and-sol/) (OpenAI 원문은 접속 차단으로 2차 정리 기준)

### MAI Code 2 · MAI Code 2 Flash (Microsoft, 11/17)
- Microsoft 자체 코딩 모델입니다. 4개 벤치마크 평균으로 GPT-6.1 Sol 성능의 98%를 비용 40%에 낸다고 주장합니다(50% 프로모션 가격 기준). 장기 에이전트 작업에는 아직 맞춰지지 않았다고 스스로 밝혔습니다.
- GitHub Copilot에서 사용 가능, Flash는 Foundry 제한 프리뷰입니다.
- 🔗 [Microsoft AI](https://microsoft.ai/news/introducing-mai-code-2-and-mai-code-2-flash/)
