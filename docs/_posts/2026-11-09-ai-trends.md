## 📌 오늘의 한 줄 요약
에이전트가 늘수록 관리 대상은 "사람의 주의력"과 "누가 만든 코드를 누가 책임지나"입니다. 작업 상태·메모리·모델 ID처럼 바뀌는 것들은 채팅창이 아니라 버전 관리되는 곳에 두세요.

## 🎯 활용 Best Practice

### "AI 브레인 프라이": 작업 큐를 git에 두고 하나씩 닫아라
- 터미널 에이전트(Claude Code, Codex)로 작업을 동시에 여러 개 열다 보면 스레드가 20개쯤 쌓입니다. 그러면 각 작업이 어디서 시작했고 무엇이 남았는지 놓치게 된다는 경험담입니다(11/8).
- 저자의 해법: 티켓마다 마크다운 파일을 만들어 코드 옆에 커밋합니다. 에이전트가 주기적으로 보드를 돌면서 조사·구현·테스트를 맡고, 민감한 변경은 브랜치에서 승인을 기다립니다. 프로덕션 배포는 사람만 합니다. 사람에게는 판단이 필요한 항목만 순위를 매긴 "오너 인박스"로 보여 줍니다.
- **적용 팁:** ① 중요한 상태는 채팅창이 아니라 git에 남기세요. ② 한 번에 한 항목만 열고, 결정한 뒤 닫으세요. 컨텍스트를 비워야 다음 항목에 집중할 수 있습니다. ③ 사람이 판단할 큐와 에이전트가 처리할 큐를 나누세요.
- 🔗 [Sergey Kuhne 블로그](https://sergeykuhne.com/blog/fighting-ai-brain-fry) · [HN 토론](https://news.ycombinator.com/item?id=50416363)

### 에이전트 메모리, 레코드 형식부터 정하라 (LoreKit 제안)
- 에이전트 메모리 포맷이 제각각이니 OpenTelemetry처럼 공통 규약을 만들자는 제안입니다(11/7). 구성은 세 가지입니다. 이름 규칙, MCP로 노출하는 연산 5개(write/read/list/search/archive), 그리고 적합성 테스트입니다.
- 메모리 레코드에는 `address`(적용 범위), `id`(같은 내용을 다시 쓰면 갱신), `lifecycle`(만료), `written_by`(작성 주체)를 둡니다. 본문은 Markdown으로 씁니다.
- **적용 팁:** 사내 메모리를 설계할 때 "어디에 적용되나·무엇과 같은 것인가·언제 무효가 되나·누가 썼나" 네 가지를 필드로 명시하세요. 사람이 쓴 것과 에이전트가 쓴 것은 신뢰도를 다르게 두세요. 공유 메모리는 프롬프트 인젝션 경로가 될 수 있으니 서명하거나 근거 코드에 연결해 두세요.
- 🔗 [LoreKit 블로그](https://www.lorekit.io/blog/open-agent-memory-format) · [HN 토론](https://news.ycombinator.com/item?id=50411467)

### 하네스 업데이트도 "모델 변경"으로 다뤄라 (Claude Code → Pi 전환기)
- 한 개발자가 Claude Code에서 오픈소스 하네스 Pi로 옮긴 이유를 정리했습니다(11/7 갱신). 올해 릴리스 244개 중 4분의 3 이상이 시스템 프롬프트나 도구 설명을 바꿨다고 합니다. 기본 Bash 도구 설명만 3,000토큰에 가깝다는 지적도 있습니다(저자 측정).
- **적용 팁:** 하네스 버전을 고정하고, 올릴 때는 사내 eval을 다시 돌리세요. 매 요청에 붙는 도구 설명은 비용이므로 쓰지 않는 도구는 끄세요. 생성된 코드는 커밋 전에 사람이 검토하는 원칙은 하네스를 바꿔도 그대로 지키세요.
- 🔗 [caleb.software](https://caleb.software/posts/claude-to-pi.html) · [HN 토론](https://news.ycombinator.com/item?id=50410107)

### 성능 작업은 "벤치마크 먼저, 목표 수치로 요청" (Simon Willison)
- SQLite `parse_number()` 확장을 C와 Rust로 만들게 해 보니 첫 C 버전이 Rust보다 느렸습니다. 측정 결과를 보여 주고 더 빠른 파서를 요청하자 개선된 버전이 나왔습니다(11/8).
- **적용 팁:** "최적화해 줘" 대신 측정 스크립트를 먼저 만들게 하세요. 그다음 "현재 X, 목표 Y" 수치와 산출물 형식(리포트, zip)을 정해 주세요.
- 🔗 [Simon Willison](https://simonwillison.net/2026/Nov/8/sqlite-parse-number-c-vs-rust/)

## ⚙️ LLM 서빙/인프라
- **llama-modchip: GPU 없이 284B MoE 실행:** llama.cpp 패치 모음입니다. DeepSeek-V4-Flash(총 284B, 활성 13B)를 1.71bpw(56.56GiB)로 압축해 64GB RAM의 Zen 5 데스크톱에서 돌립니다. 디코드는 초당 9.1~14.7토큰입니다. 수치는 대부분 작성자가 직접 측정했고, 전용 바이너리가 필요합니다. Top-4/5 모드는 품질을 일부 희생합니다.
  - **적용 팁:** 활성 파라미터가 작은 MoE는 "메모리 용량 > GPU" 문제로 바뀝니다. 로컬 에이전트용이라면 KV 캐시 스냅샷으로 컨텍스트를 빠르게 복원하는 방식도 참고할 만합니다.
  - 🔗 [GitHub](https://github.com/synchopate/llama-modchip) · [HN 토론](https://news.ycombinator.com/item?id=50411961)

## 💰 수익화
- **OpenRouter 8일간 가격 변동 분석:** 10/28~11/5 사이 양쪽 스냅샷에 모두 있던 665개 경로 중 35개의 가격이 바뀌었습니다. 확정 경로 29개 중 13개는 올랐고 7개는 내렸습니다. 인상은 Llama·Qwen 같은 오픈 웨이트 경로에 몰렸습니다(예: Llama 3.1 70B $0.40→$0.72/1M). 경로 27개는 목록에서 빠졌습니다.
  - **적용 팁:** 별칭이 아니라 구체적 모델 ID를 고정하세요. 모델 목록과 입력·출력 단가를 주기적으로 diff하세요. 마켓플레이스 가격은 벤더 정가가 아니니 결정 전에 원문을 확인하세요.
  - 🔗 [Digital Applied](https://www.digitalapplied.com/blog/ai-api-price-changes-retirements-november-2026)

## 🏢 업계 동향
- **Goldman Sachs, 코딩 에이전트를 엔지니어 전용으로:** 10월 내부 지침이 바뀌어 Claude Code와 GitHub 도구를 대부분의 트레이더·뱅커가 더는 쓸 수 없습니다. 이유로는 생산성과 리스크 관리가 꼽혔습니다. 검토·테스트·배포 통제를 거치지 않은 도구가 일상 업무에 쓰였고, 정보 차단벽(Chinese wall)도 우려됐다고 합니다. 7월 CIO가 비개발자 "바이브 코딩"을 칭찬했던 것과는 정반대 방향입니다.
  - **시사점:** 비개발자에게 에이전트를 열어 줄 때는 "에이전트가 만든 코드의 책임 엔지니어"와 기존 배포 통제를 함께 정해 두세요.
  - 🔗 [The State of AI](https://www.thestateofai.com/news/goldman-sachs-claude-code-traders-bankers) · [AI Weekly](https://aiweekly.co/alerts/goldman-sachs-pulls-claude-code-and-github-copilot-from-traders-and-bankers) · [HN 토론](https://news.ycombinator.com/item?id=50415628) (Bloomberg 보도를 2차 출처로 확인)
