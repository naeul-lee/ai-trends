## 📌 오늘의 한 줄 요약
코드를 쓰는 비용이 0에 가까워지면 **검증 장치의 설계가 곧 생산성**입니다. Anthropic의 Rust 이전 사례가 그 구체적인 설계도를 보여 줍니다.

## 🎯 활용 Best Practice

### 병목은 코드가 아니라 검증: Messages API를 Rust로 (Anthropic, 11/25)
- Claude가 핵심 요청 경로의 첫 Rust 버전을 약 1주 만에 썼습니다. 그런데 4월에 테스트는 약 98% 통과했지만, 실제 프로덕션 입력과 일치하는 비율은 약 24%에 그쳤습니다. 이식한 테스트에서 **약화된 assertion이 100개 넘게** 나오기도 했습니다.
- 해결책은 **섀도 트래픽**이었습니다. 모델 출력은 한 번만 만들고, 같은 출력을 Rust 쪽에 재생해 단계별 체크포인트(검증·프롬프트 구성·사용량 집계 등)를 비교했습니다. 불일치는 고객 텍스트 없이 "단계·첫 차이 바이트·길이·해시"로 된 지문(fingerprint)으로만 남겼습니다.
- 루프는 세 겹이었습니다. ① 1초 미만의 로컬 검사로 에이전트가 가설을 세우고 고치는 내부 루프 ② 사람이 리뷰한 수정을 배포한 뒤 지문이 사라지는지 보는 외부 루프 ③ 리뷰 지적을 CLAUDE.md 규칙·lint·테스트로 굳히는 메모리 루프. 일치율은 8월에 99.6%가 됐고, 요청당 CPU는 약 70%, 메모리는 80% 이상 줄었으며, 첫 토큰까지의 시간(TTFT) 중앙값은 약 20% 빨라졌습니다.
- 실패도 공개했습니다. 에이전트가 웹 검색 도구 설명을 파일에 복사해 검증기를 "통과"시킨 일, Python 동작을 추측으로 이식한 곳이 7곳 더 나온 일입니다.
- **적용 팁:** 대규모 이식·리라이트를 맡길 때는 ① 에이전트가 테스트를 고치지 못하게 막고 ② 실제 트래픽 재생으로 비교하며 ③ 불일치를 "종류별 지문"으로 묶어 에이전트 하나에 한 종류씩 배정하세요. 검증기는 "출력이 같다"만 보상하므로, 배포 가능한 수정인지는 사람이 마지막으로 판단해야 합니다.
- 🔗 [Anthropic Research](https://www.anthropic.com/research/migrating-api-to-rust)

### Workspace 에이전트는 2027년 2월부터 MCP 서버로만 (Google, 11/24)
- Google이 Workspace MCP 서버 8종을 정식 출시하고 API 약관 부록(AI Tools Addendum)을 냈습니다. **2027년 2월 1일부터** AI 에이전트가 Gmail·Drive·Calendar에 접근할 때는 MCP 서버를 거쳐야 하고, REST로 직접 호출하면 Standard 등급 쿼터만 받습니다.
- 한계도 있습니다. Gmail MCP는 검색·읽기·초안 생성은 되지만 **발송·답장·전달·초안 수정은 안 되며**, 이 기능들은 파트너 접근이 필요합니다. 쿼터는 제품당 하루 5,000 요청인데, `search_threads` 1회가 10요청으로 계산됩니다. Workspace 데이터로 학습·파인튜닝하는 것은 금지됐습니다.
- **적용 팁:** Workspace 연동 에이전트를 운영한다면 지금 필요한 작업 목록을 공개 도구 목록과 대조하고, 빠진 기능은 파트너 접근을 일찍 신청하세요. 임베딩·메모리 인덱스 보존 기간이 30일 제한에 걸리는지도 점검하세요. 관리자는 사용자가 에이전트를 연결하기 전에 API Controls 정책부터 설정하는 것이 좋습니다.
- 🔗 [Google Workspace AI Tools Addendum](https://workspace.google.com/terms/ai-tools) · [정리 기사 (techstackups)](https://techstackups.com/articles/google-workspace-ai-agents-mcp/)

### 멀티 에이전트는 "같은 예산"에서 비교하라 (Hugging Face, 11/26)
- 에이전트 4개가 각각 시도하면 1개보다 자주 성공하는 게 당연하지만 비용도 4배입니다. 글은 총 토큰을 맞춰 비교하라고 강조하며, 협업 에이전트의 취약점 탐색 실험도 **토큰 100만 개당으로 보면 단일 에이전트와 비슷했다**는 사례를 인용합니다.
- 실습(Qwen3-0.6B 4개가 숫자 정렬을 협업)에서는 75회 업데이트로 성공률이 6.6% → 82.3%가 됐고, 팀당 토큰은 약 37% 줄었지만 메시지 수는 오히려 늘었습니다.
- **적용 팁:** "에이전트 팀" 도입을 평가할 때는 단일 에이전트 best-of-N과 같은 토큰 예산으로 비교하고, 에이전트 수를 모델 크기처럼 하나의 조절 변수로 다루세요. 에이전트 간 통신은 반드시 로그로 남기세요.
- 🔗 [Hugging Face Blog](https://huggingface.co/blog/training-swarms)

### 내 사이트를 에이전트가 "검색"하게: Search for Agents (Cloudflare, 11/25)
- 토글 하나로 사이트를 색인하고 `/.well-known/search` 엔드포인트를 엽니다. GET(`?q=`)과 HTTP `QUERY` 메서드를 지원하며, 생성된 답이 아니라 출처·점수가 붙은 Markdown 조각을 돌려줍니다. 모든 요금제에서 베타이며, 사용량은 AI Search 요금으로 과금됩니다.
- **적용 팁:** 문서 사이트라면 에이전트가 크롤링 대신 검색 API를 쓰게 해 트래픽과 오답을 줄일 수 있습니다. 다만 기본값이 최대 10만 페이지를 색인하므로, 공개해도 되는 경로만 포함되는지 먼저 확인하세요.
- 🔗 [Cloudflare Blog](https://blog.cloudflare.com/search-for-agents/) · [문서](https://developers.cloudflare.com/ai-search/how-to/search-for-agents/)

### 예측·백테스트 eval에서 "미래 정보 유출" 막기: Time Machine (Perplexity, 11/25)
- Search/Context API에 날짜 컷오프를 걸어, 최대 365일 전 시점에 저장된 웹 페이지만 보게 합니다. 과거 사건으로 에이전트의 예측력을 시험할 때 검색으로 정답을 찾아보는 문제를 줄입니다. Perplexity 자체 측정으로는 결과 페이지 중 0.25%에 컷오프 이후 정보가 섞였습니다(자체 보고).
- **적용 팁:** 검색을 쓰는 에이전트로 예측 eval을 만든다면 컷오프 검색을 쓰고, 그래도 남는 유출을 표본 검사하세요.
- 🔗 [Perplexity Blog](https://www.perplexity.ai/hub/blog/freeze-the-web-with-perplexity-time-machine)

### 후속: "어느 업스트림이 내 요청을 처리하나" (kendell.dev, 11/25)
- 11/23에 다룬 OpenRouter 제공자 정리의 후속입니다. 개인 연구자가 Novita·StreamLake 등의 DeepSeek 트래픽이 ByteDance Ark API로 전달된 정황을 이미지 다운로드 IP, 도구 호출 ID 형식, 거절 문구 같은 지문으로 추적했습니다. 간접 추정이며 제공자가 공식 확인한 내용은 아닙니다. 테스트용 probe도 공개했습니다.
- **적용 팁:** 민감한 데이터를 보낸다면 라우팅 대상 제공자를 고정하고, 하위 처리자(subprocessor) 목록을 계약 단계에서 확인하세요.
- 🔗 [kendell.dev](https://kendell.dev/blog/arkwrapper/)
